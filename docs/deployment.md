# GridProof deployment workflow

This guide is the reproducible path for taking GridProof from a clean checkout to a public demo deployment.

The intended free-tier stack is:

- Web app: Vercel, serving `apps/web`.
- API: Render web service, serving `apps/api`.
- Agent worker: Render free web service, serving `apps/agent-worker` with a lightweight `/health` endpoint while it processes background jobs.
- Postgres/Auth: Supabase production project.
- Redis/queues/rate limits: Upstash Redis production database.
- Contracts: BOT Chain testnet or mainnet, using the deployment manifest generated by the contracts package.
- Keep-warm: GitHub Actions scheduled ping against the deployed API health endpoint.

Use separate production Supabase and Upstash projects from local development. Do not point a public demo at the local Docker Postgres/Redis services.

## 1. Prepare the shared production services

### Supabase

1. Create a new Supabase project named `gridproof-prod` or `gridproof-demo`.
2. Copy the project Postgres connection string.
3. Copy the Auth JWT secret from the Supabase dashboard.
4. Keep these values for the API and worker:
   - `DATABASE_URL`
   - `SUPABASE_URL`
   - `SUPABASE_JWT_SECRET`

Run migrations against the production database from a trusted machine:

```bash
DATABASE_URL="<supabase-postgres-url>" pnpm db:migrate
```

Verify that production Supabase and Upstash are reachable and have the expected GridProof schema/queue backing:

```bash
DATABASE_URL="<supabase-postgres-url>" \
REDIS_URL="<upstash-redis-url>" \
pnpm deployment:data
```

This checks Postgres connectivity, the `pgcrypto` extension, demo-critical tables, demo-critical indexes, the Redis URL scheme, and a Redis `PING`. Run it before deploying the API/worker and again after changing Supabase or Upstash credentials.

Optional demo seed:

```bash
DATABASE_URL="<supabase-postgres-url>" pnpm db:seed
```

Only seed production if the team wants known demo zones/providers visible at launch.

### Upstash Redis

1. Create a new Upstash Redis database named `gridproof-prod` or `gridproof-demo`.
2. Copy the Redis URL.
3. Use it as `REDIS_URL` for both the API and the worker.

The API uses Redis for ingestion rate limiting and job queues. The worker consumes those queues, so both services must point at the same production Redis database.

## 2. Deploy BOT Chain contracts

GridProof contracts are configured for local Anvil, BOT Chain testnet, and BOT Chain mainnet. The official BOT Chain network settings are:

| Network | Chain ID | RPC | Explorer | Manifest |
| --- | ---: | --- | --- | --- |
| Testnet | 968 | `https://rpc.bohr.life` | `https://scan.bohr.life` | `smart-contracts/deployments/botchainTestnet.json` |
| Mainnet | 677 | `https://rpc.botchain.ai` | `https://scan.botchain.ai` | `smart-contracts/deployments/botchainMainnet.json` |

Always confirm `cast chain-id --rpc-url <rpc>` before a broadcast in case the network operator changes an endpoint.

Do not guess BOT Chain values in source code or docs.

From the repository root:

```bash
cd smart-contracts
cp .env.example .env
```

Fill `.env` with the network values and the deploy parameters documented in
`smart-contracts/.env.example`:

- `BOTCHAIN_RPC_URL` and `BOTCHAIN_CHAIN_ID`. If you keep both networks in one `.env`, suffix them per network (`BOTCHAIN_RPC_URL_TESTNET`, `BOTCHAIN_RPC_URL_MAINNET`) and use the matching name on the forge command line.
- `BOTCHAIN_EXPLORER_API_URL` and `BOTCHAIN_EXPLORER_URL`
- `BOTCHAIN_EXPLORER_API_KEY`, if explorer verification requires one
- `DEPLOYER_PRIVATE_KEY`, or use `--ledger` / `--account <keystore>` instead
- `GRIDPROOF_NETWORK`, which names the manifest file
- `GRIDPROOF_ADMIN_ADDRESS` and `GRIDPROOF_RELAYER_ADDRESS`, which must differ
- optional policy params `GRIDPROOF_EPOCH_DURATION_SECONDS`, `GRIDPROOF_SLASH_POLICY_CAP`, `GRIDPROOF_MINIMUM_STAKE`, `GRIDPROOF_WITHDRAW_COOLDOWN_SECONDS`, and `GRIDPROOF_ZONE_IDS`. For existing zones, populate `GRIDPROOF_ZONE_IDS` with the database's exact `zone_key` values; `0x` + 64-hex values are preserved rather than hashed again.

Keep `.env` local. Never commit populated secrets or private keys.

Validate before deploying, from the repository root:

```bash
pnpm contracts:test
forge build --root smart-contracts
```

Deploy the chosen network from `smart-contracts/`. Load `.env` into the shell
first: `forge script` reads the `GRIDPROOF_*` parameters from its own environment,
and the shell must expand `$BOTCHAIN_RPC_URL` before forge starts.

```bash
set -a && . ./.env && set +a
forge script script/Deploy.s.sol:Deploy \
  --rpc-url "$BOTCHAIN_RPC_URL" \
  --private-key "$DEPLOYER_PRIVATE_KEY" \
  --broadcast
```

Swap `--private-key` for `--ledger` or `--account <keystore>` on mainnet.
`Deploy.s.sol` calls bare `vm.startBroadcast()`, which does not pick up
`DEPLOYER_PRIVATE_KEY` on its own, so the signer must be passed as a flag.

Do not skip the `set -a && . ./.env && set +a` line. Forge loads `.env` after it
starts, but your shell expands `$BOTCHAIN_RPC_URL` before that. If the variable
is unset in the shell, forge receives an empty `--rpc-url`, falls back to
`http://localhost:8545`, and fails with:

```text
Error: Internal transport error: Connection refused (os error 111)
```

That error means the shell variable was empty, not that the BOT Chain endpoint is
down. Confirm the value reached the shell with `echo "$BOTCHAIN_RPC_URL"` before
rerunning.

Alternatively, define the endpoint as a forge alias so no shell expansion is
involved. In `smart-contracts/foundry.toml`:

```toml
[rpc_endpoints]
botchain_testnet = "${BOTCHAIN_RPC_URL_TESTNET}"
botchain_mainnet = "${BOTCHAIN_RPC_URL_MAINNET}"
```

Then pass `--rpc-url botchain_testnet`. Forge resolves the alias against `.env`
itself, so an unset shell variable surfaces as a named-endpoint error instead of
a silent localhost fallback. The `GRIDPROOF_*` parameters still require `.env` to
be loaded into the shell.

`Deploy.s.sol` also seeds the `NodeRegistry` zone allowlist from
`GRIDPROOF_ZONE_IDS` in the same run, but only when the broadcasting account is
`GRIDPROOF_ADMIN_ADDRESS`. With a multisig admin the script logs a warning and
skips seeding; call `NodeRegistry.addZone` from the multisig for each zone
afterwards.

For the selected `GRIDPROOF_NETWORK`, the deploy script writes:

```text
smart-contracts/deployments/<GRIDPROOF_NETWORK>.json
```

That manifest includes:

- network and chain ID
- deployment timestamp
- admin multisig
- backend relayer wallet
- `NodeRegistry`, `UptimeAttestation`, and `ReputationEscrow` addresses
- constructor/policy params

Copy the manifest values into the API runtime env:

- `BOTCHAIN_RPC_URL`
- `BOTCHAIN_CHAIN_ID`
- `BOTCHAIN_EXPLORER_BASE_URL`
- `BOTCHAIN_NODE_REGISTRY_ADDRESS`
- `BOTCHAIN_UPTIME_ATTESTATION_ADDRESS`
- `BOTCHAIN_REPUTATION_ESCROW_ADDRESS`
- `RELAYER_PRIVATE_KEY`

Confirm the env network matches the contract manifest. Testnet contract addresses must not be paired with mainnet chain IDs or RPC URLs, and mainnet addresses must not be paired with testnet RPC URLs.

Run the manifest/env preflight before deploying or redeploying the API:

```bash
GRIDPROOF_CONTRACT_MANIFEST_PATH=smart-contracts/deployments/botchainTestnet.json \
BOTCHAIN_CHAIN_ID=<manifest-chain-id> \
BOTCHAIN_NODE_REGISTRY_ADDRESS=<manifest-node-registry> \
BOTCHAIN_UPTIME_ATTESTATION_ADDRESS=<manifest-uptime-attestation> \
BOTCHAIN_REPUTATION_ESCROW_ADDRESS=<manifest-reputation-escrow> \
pnpm deployment:contracts
```

The repository also provides fixed-path shortcuts:

```bash
pnpm deployment:contracts:testnet
pnpm deployment:contracts:mainnet
```

The mainnet command expects `smart-contracts/deployments/botchainMainnet.json`, which is created only by a successful mainnet deployment. A missing-file failure before deployment is expected; never copy or rename the testnet manifest to satisfy it.

### Mainnet pre-broadcast gate

Before adding `--broadcast`, confirm all of the following:

```bash
cd smart-contracts
set -a && . ./.env && set +a
test "$(cast chain-id --rpc-url "$BOTCHAIN_RPC_URL")" = "677"
test "$GRIDPROOF_NETWORK" = "botchainMainnet"
test "${GRIDPROOF_ADMIN_ADDRESS,,}" != "${GRIDPROOF_RELAYER_ADDRESS,,}"
DEPLOYER_ADDRESS=$(cast wallet address --private-key "$DEPLOYER_PRIVATE_KEY")
cast balance "$DEPLOYER_ADDRESS" --rpc-url "$BOTCHAIN_RPC_URL"
```

The balance must be non-zero and sufficient for three deployments. Prefer a hardware wallet or encrypted Foundry keystore on mainnet instead of a raw `DEPLOYER_PRIVATE_KEY`.

The preflight fails on malformed manifests, zero or duplicate contract addresses, admin/relayer wallet reuse, chain-ID mismatches, and API contract-address mismatches. It warns when API env values are not set yet, which is acceptable only before wiring Render secrets.

### Explorer verification

After deployment, verify all three contracts on the BOT Chain explorer using the official explorer API/browser URLs:

```bash
forge verify-contract 0x78624f4025A3B41524c2EdCD99270500a1aC9477 src/NodeRegistry.sol:NodeRegistry \
  --chain-id "$BOTCHAIN_CHAIN_ID" \
  --verifier blockscout \
  --verifier-url "https://scan.bohr.life/api/" \
  --constructor-args "$(cast abi-encode 'constructor(address)' 0x53f04Af7ff379a5Cef4a923e1a2B368791AaF3d1)"

forge verify-contract 0xB3A976CC574fdBf1488a3912B244433244e3f189 src/UptimeAttestation.sol:UptimeAttestation \
  --chain-id "$BOTCHAIN_CHAIN_ID" \
  --verifier blockscout \
  --verifier-url "https://scan.bohr.life/api/" \
  --constructor-args "$(cast abi-encode 'constructor(address,address,uint64)' 0x53f04Af7ff379a5Cef4a923e1a2B368791AaF3d1 0x79955f9ABadCeb277596EE06D65981ce6377aB12 3600)"

forge verify-contract 0x2E084a59dA63b5B2E0E44DA6990aa03A10Dfe2fc src/ReputationEscrow.sol:ReputationEscrow \
  --chain-id "$BOTCHAIN_CHAIN_ID" \
  --verifier blockscout \
  --verifier-url "https://scan.bohr.life/api/" \
  --constructor-args "$(cast abi-encode 'constructor(address,address,address,uint256,uint256,uint64)' 0x53f04Af7ff379a5Cef4a923e1a2B368791AaF3d1 0x79955f9ABadCeb277596EE06D65981ce6377aB12 0x78624f4025A3B41524c2EdCD99270500a1aC9477 500000000000000000 100000000000000000 259200)"
```

Only replace placeholders with values from the deployment manifest and `.env`.
Add `--etherscan-api-key "$BOTCHAIN_EXPLORER_API_KEY"` if the explorer requires
a key, and `--verifier blockscout` if it exposes a Blockscout-style API rather
than an Etherscan-style one.

## 3. Deploy API and worker on Render

The repo includes a Render blueprint at:

```text
infrastructure/render.yaml
```

It defines:

- `gridproof-api`, a Docker web service using `infrastructure/docker/api.Dockerfile`.
- `gridproof-agent-worker`, a Docker web service using `infrastructure/docker/agent-worker.Dockerfile`.
- API health checks against `/api/v1/health`.
- Worker health checks against `/health`.

Render's free plan is available for web services, not background workers. The GridProof worker therefore exposes `/health` and runs as a web service on free tier. It still consumes the `agent-review` BullMQ queue exactly like a background worker.

### Render setup

1. Push the repository to GitHub.
2. In Render, choose “Blueprint” and select this repo.
3. Use `infrastructure/render.yaml` as the blueprint file.
4. Create both services.
5. Fill every `sync: false` environment variable from the production secret stores.
6. Deploy the worker after the API has a valid `DATABASE_URL` and `REDIS_URL`.

### API environment variables

Required:

- `NODE_ENV=production`
- `PORT=4000`
- `API_VERSION=0.1.0`
- `CORS_ORIGINS=<vercel-origin>`
- `DATABASE_URL=<supabase-postgres-url>`
- `REDIS_URL=<upstash-redis-url>`
- `SUPABASE_URL=<supabase-project-url>`
- `SUPABASE_JWT_SECRET=<supabase-jwt-secret>`
- `GRIDPROOF_AUTH_INVITE_CODE=<private-provider-onboarding-code>`
- `TELEMETRY_HMAC_SECRET=<strong-random-secret>`
- `WHATSAPP_WEBHOOK_SECRET=<whatsapp-or-adapter-hmac-secret>`
- `BOTCHAIN_RPC_URL=<bot-chain-rpc-url>`
- `BOTCHAIN_CHAIN_ID=<bot-chain-chain-id>`
- `BOTCHAIN_EXPLORER_BASE_URL=<bot-chain-explorer-url>`
- `BOTCHAIN_NODE_REGISTRY_ADDRESS=<manifest-node-registry>`
- `BOTCHAIN_UPTIME_ATTESTATION_ADDRESS=<manifest-uptime-attestation>`
- `BOTCHAIN_REPUTATION_ESCROW_ADDRESS=<manifest-reputation-escrow>`
- `RELAYER_PRIVATE_KEY=<funded-backend-relayer-key>`

Recommended:

- `GRIDPROOF_EVIDENCE_MODE=hybrid`
- `INGEST_RATE_LIMIT_MAX=60`
- `INGEST_RATE_LIMIT_WINDOW_MS=60000`
- `REDIS_RATE_LIMIT_TIMEOUT_MS=500`
- `NOTIFICATION_WEBHOOK_URL=<optional-demo-alert-webhook>`
- `GRIDPROOF_DEMO_ENABLED=true` enables the public Judge Demo Lab API in production.
- Keep `GRIDPROOF_DEMO_ALLOW_CHAIN_WRITE` unset or `false` on mainnet so synthetic judge runs stop at a clearly labelled proof preview. Enable it only on an isolated demo network when synthetic commitments are intentional.
- `NOTIFICATION_WEBHOOK_TOKEN=<optional-webhook-token>`
- `SENTRY_DSN=<optional-api-sentry-dsn>`
- `SENTRY_ENVIRONMENT=production`
- `SENTRY_RELEASE=gridproof-api@0.1.0`
- `SENTRY_TRACES_SAMPLE_RATE=0`

`CORS_ORIGINS` is required in production. Set it to the exact Vercel URL, and add any preview/demo aliases as a comma-separated list. Do not use `*`.

### Worker environment variables

Required:

- `NODE_ENV=production`
- `PORT=4101`
- `DATABASE_URL=<same-supabase-postgres-url-as-api>`
- `REDIS_URL=<same-upstash-redis-url-as-api>`
- `LLM_BASE_URL=<model-provider-base-url>`
- `LLM_API_KEY=<model-provider-key>`
- `LLM_ANALYSIS_MODEL=<fast-analysis-model>`
- `LLM_VERIFICATION_MODEL=<strong-verification-model>`

Recommended:

- `LOG_LEVEL=info`

## 4. Deploy web on Vercel

The repo includes Vercel config at:

```text
vercel.json
```

It builds only `apps/web` and serves the Vite output from `apps/web/dist`.

### Vercel setup

1. Import the GitHub repo into Vercel.
2. Leave the framework as Vite.
3. Confirm the build settings from `vercel.json`:
   - Install command: `pnpm install --frozen-lockfile`
   - Build command: `pnpm --filter @gridproof/shared-types build && pnpm --filter @gridproof/web build`
   - Output directory: `apps/web/dist`
4. Set the web environment variables.
5. Deploy.
6. Copy the production Vercel URL back into the API `CORS_ORIGINS`.
7. Redeploy the API after updating CORS.

### Web environment variables

Required:

- `VITE_API_BASE_URL=https://<gridproof-api-host>/api/v1`

Recommended:

- `VITE_DEMO_AUTH_TOKEN=<short-lived-demo-reviewer-jwt>`
- `VITE_SENTRY_DSN=<optional-web-sentry-dsn>`
- `VITE_SENTRY_ENVIRONMENT=production`
- `VITE_SENTRY_RELEASE=gridproof-web@0.1.0`
- `VITE_SENTRY_TRACES_SAMPLE_RATE=0`

Do not put server secrets, private keys, database URLs, Redis URLs, or Supabase JWT secrets in Vercel. Vite exposes `VITE_*` values to the browser bundle.

## 5. Enable keep-warm ping

Free Render web services can sleep. The repo includes:

```text
.github/workflows/keep-warm.yml
```

Add this GitHub repository variable:

- `GRIDPROOF_API_HEALTH_URL=https://<gridproof-api-host>/api/v1/health`

The workflow pings the API every 10 minutes and can also be run manually from GitHub Actions.

If the project moves to a paid always-on service, remove the scheduled workflow or clear `GRIDPROOF_API_HEALTH_URL`.

## 6. Production smoke test

Run this after every redeploy:

```bash
GRIDPROOF_API_BASE_URL=https://<gridproof-api-host> \
GRIDPROOF_WEB_URL=https://<gridproof-web-host> \
GRIDPROOF_WORKER_BASE_URL=https://<gridproof-agent-worker-host> \
GRIDPROOF_PROOF_ZONE_ID=<demo-zone-uuid-or-zone-key> \
GRIDPROOF_PROOF_EPOCH=latest \
pnpm deployment:verify
```

`GRIDPROOF_API_BASE_URL` may be either the service root or the `/api/v1` URL. `GRIDPROOF_WEB_URL`, `GRIDPROOF_WORKER_BASE_URL`, and `GRIDPROOF_PROOF_ZONE_ID` are optional for local smoke checks but should be set for the final rehearsal. `GRIDPROOF_PROOF_EPOCH` defaults to `latest`.

The verifier checks:

- API `/health`, `/metrics`, `/readiness`, `/zones`, and `/providers`.
- API `/chain/proof/:zoneId/:epoch`, when `GRIDPROOF_PROOF_ZONE_ID` is set.
- Web frontend HTML loads and does not expose a `localhost` API reference in the app shell.
- Agent worker `/health` and `/readiness`, when `GRIDPROOF_WORKER_BASE_URL` is set.

If `/api/v1/readiness` or worker `/readiness` returns `503`, the command fails and prints the redacted missing environment variable names for required demo categories such as `DATABASE_URL`, `REDIS_URL`, `SUPABASE_JWT_SECRET`, telemetry/webhook HMAC secrets, LLM proxy configuration, and BOT Chain relayer configuration.

If the team intentionally accepts an optional degraded readiness item for a rehearsal, set:

```bash
GRIDPROOF_ALLOW_DEGRADED_READINESS=true
```

Do not use the degraded override for the final live run unless the trade-off is explicitly documented.

For the final BOT Chain proof run, also require a confirmed transaction:

```bash
GRIDPROOF_REQUIRE_CONFIRMED_PROOF=true
```

With that flag, `pnpm deployment:verify` fails unless the deployed proof response includes an epoch score, a chain commitment with `status = confirmed`, a transaction hash, block number, and explorer URL.

Then open the Vercel URL in a browser and verify:

- The homepage loads without console CORS errors.
- The proof explorer shows pending or confirmed proof data.
- Provider onboarding returns BOT Chain registration instructions and links for the configured network.
- A reporter/reviewer demo token can create and review an outage report.
- Operations counters update after telemetry/report activity.
- The Operations page shows readiness as `ready`, or only `degraded` for explicitly accepted optional items.
- API exceptions appear in Sentry if Sentry DSNs are configured.

Phone/mobile check:

1. Turn off Wi-Fi on a phone.
2. Open the Vercel production URL on mobile data.
3. Confirm the dashboard renders and calls the deployed API, not `localhost`.
4. Submit or review one demo action.
5. Save screenshots of the public URL, proof explorer, and BOT Chain explorer link for the demo script.

## 7. Redeploy from scratch checklist

From a clean checkout, a teammate should be able to:

1. Install dependencies with `pnpm install --frozen-lockfile`.
2. Run local checks:

   ```bash
   pnpm test
   pnpm lint
   pnpm build
   pnpm foundry:test
   ```

3. Create production Supabase and Upstash projects.
4. Run `DATABASE_URL="<supabase-postgres-url>" pnpm db:migrate`.
5. Run `DATABASE_URL="<supabase-postgres-url>" REDIS_URL="<upstash-redis-url>" pnpm deployment:data`.
6. Deploy BOT Chain contracts and record the manifest.
7. Create Render services from `infrastructure/render.yaml`.
8. Create the Vercel frontend from `vercel.json`.
9. Set `CORS_ORIGINS` to the Vercel production URL and redeploy the API.
10. Set `GRIDPROOF_API_HEALTH_URL` in GitHub repository variables.
11. Run `pnpm deployment:verify` and the phone/mobile check.
12. Fill the demo evidence manifest and run:

   ```bash
   GRIDPROOF_DEMO_EVIDENCE_PATH=docs/demo-evidence.json pnpm deployment:evidence
   ```

Demo-readiness criteria:

- Foundry contract tests pass locally (`pnpm contracts:test`).
- Deployment manifest exists for the chosen BOT Chain network.
- Post-deployment role verification passes (the `cast call hasRole` checks in
  [`security-checklist.md`](./security-checklist.md#post-deployment-role-verification)).
- Admin address is a team multisig, not a single laptop EOA.
- Relayer wallet has only the operational funds needed for demo transactions.
- Supabase and Upstash production projects are separate from local development.
- `pnpm deployment:data` passes against production Supabase and Upstash.
- API and worker point at the same production `DATABASE_URL` and `REDIS_URL`.
- Contract addresses, chain ID, RPC URL, and explorer URL all point at the same BOT Chain network.
- `CORS_ORIGINS` is set to deployed frontend origins only.
- `/api/v1/readiness` returns `ready` before the live run, or any `degraded` checks are intentional and documented.
- `pnpm deployment:verify` exits successfully against the public API, web, worker, and known demo proof URLs.
- `GRIDPROOF_REQUIRE_CONFIRMED_PROOF=true pnpm deployment:verify` passes for the final run after BOT Chain confirmation indexing.
- Two passing deployed-stack rehearsals and the backup recording/screenshot set are recorded in a demo evidence manifest that passes `pnpm deployment:evidence`.
- Optional Sentry DSNs are set if the team wants live exception capture during demo rehearsal.
- Public web and API URLs work from a phone on mobile data.
